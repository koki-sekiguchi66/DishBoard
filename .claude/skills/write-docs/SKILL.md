# ドキュメントを書く

## 0. 先に確認すること

- **この内容の読者は誰か。** ここで置き場所が決まる（§1）
- 既存の同種ドキュメントを1つ読む。`docs-public/decisions.md` か `docs-public/google-authentication.md`
- 既に同じことを書いた文書がないか。**新規作成より既存の更新を優先する**
- 公開資料の入口は `docs-public/README.md`。アーキテクチャの本文は
  `docs-public/architecture.md` を更新する（ルートの `ARCHITECTURE.md` は案内のみ）

## 1. 置き場所を決める

**このリポジトリは public 公開を前提とする。就活で採用担当者が読む可能性がある。**

| | `docs-public/`（Git 追跡） | `docs/`（Git 管理外） |
|---|---|---|
| 読者 | 第三者・将来の保守担当・採用担当 | 自分だけ |
| 性格 | 「これは何で、なぜこうなっているか」 | 「自分は何に詰まり、どう切り分けたか」 |

| 内容 | `docs-public/` | `docs/` |
|---|---|---|
| 設計判断とその理由 | **必ず書く** | 補足のみ |
| 仕様・API・データモデル | 書く | 簡略でよい |
| 制約・今後の課題 | 書く | 書く |
| 環境変数の**名前** | 書く | 書く |
| 環境変数の**実値** | **書かない** | **書かない** |
| 実ドメイン・VM名・アカウント名 | **書かない** | 避ける |
| 実際に失敗したコマンド | 一般化した教訓だけ | そのまま書く |
| 詰まった過程・感想 | 書かない | 書く |
| 再現可能な手順 | 一般手順として書く | 自分向けの詳細でよい |

判断に迷ったら: **「他人が読んで役に立つか」なら公開、「自分の体験の記録」ならローカル。**

## 2. `docs-public/` に書くときの型

### ADR（設計判断の記録）

`docs-public/decisions.md` に **#連番** で追記する。必ずこの構成で書く。

```markdown
## #N. <決定を一文で。体言止めにしない>

**決定**
何をどう決めたか。3〜5行。

**背景**
なぜ判断が必要になったか。何が問題だったか。

**検討した代替案**
1. 案A
2. 案B（採用）

**選んだ理由**
なぜ他を捨てたか。**却下理由まで書く。**

**トレードオフ**
- 得たもの:
- 失ったもの:
- 受容の根拠:
```

守ること:

- **「一般的にはこうする」から外れた判断には、必ず理由を書く。** ここが読者の知りたい所
- **失ったものを正直に書く。** トレードオフのない設計判断は存在しない
- 受容の根拠は**このアプリの実態**（研究室10〜20名 / 1GB VM / PWA）に紐づける
- 未実装の方針なら、見出し直下に `> 状態: **方針決定のみ。未実装**` と書く
- 実測値があるなら書く（「見積り」より「`docker stats` で 66.8MiB」の方が強い）

### 機能ドキュメント

大きな機能は `docs-public/<機能名>.md` に分ける（例: `google-authentication.md`）。
ADR には要約と判断だけ残し、詳細はこちらへ置いてリンクする。

推奨する並び:

1. 前提の整理（混同されやすい概念があるなら最初に分離する）
2. 機能一覧（表）
3. データモデル / API（表とスキーマ）
4. **設計判断**（なぜこうしたか）
5. 制約 / 今後の候補
6. 保守上の原則（箇条書きで再掲）

## 3. `docs/` に書くときの型

**実況として書く。** 整えすぎない。将来の自分が同じ問題を踏んだとき助かる形にする。

問題ごとに **症状 → 切り分け → 原因 → 対処 → 学び** で書く。
特に **切り分け**（どう原因を絞ったか）を厚く書く。結論だけなら価値が薄い。

- 再発しうる問題は `docs/troubleshooting.md` に**症状から引ける形**で追記する
- ある作業全体の記録は `docs/<作業名>-log.md` に分ける
- 冒頭に `> この文書はリモートリポジトリへ push しない` と明記する

## 4. 書いてはいけないもの

`docs/` は Git 管理外だが、**流出したときに困るものは最初から書かない**。

- `.env` の中身・API キー・パスワード・トークン・credential
- 実際のドメイン名、VM のホスト名・ユーザー名、IP アドレス
- 利用者の氏名・メールアドレス・体重や食事内容などの健康情報

コマンド例では `<sub>.duckdns.org` `<POSTGRES_USER>` のようなプレースホルダを使う。

## 5. 実装を終えたら（★ここまでが実装）

**コードとテストが通っただけでは完了ではない。** 実装と同じ変更の中で記録まで行う。

### 5-1. まず「嘘になった記述」を探す

**新しく書くより先に、古い記述を潰す。** 機能を足すと、それまで
「できない」「未実装」と書いていた箇所が嘘になる。これが最も見落としやすい。

```bash
rg -n '未実装|できない|していない|見送|localStorage' docs-public/ backend/CLAUDE.md frontend/CLAUDE.md
```

該当したら次のいずれかを行う。

| 状況 | 対処 |
|---|---|
| 「今後の課題」の表に載っている | **その行を消す** |
| 過去の ADR の決定を部分的に変えた | 古い ADR の冒頭に `> 一部変更: 〜（#N）` と追記。**本文は書き換えない** |
| 構成図・フロー図が古くなった | `docs-public/architecture.md` / `*/CLAUDE.md` を更新 |
| MCP ツールの description の前提が変わった | **description を直す**（Claude が読む唯一の仕様書） |

**古い ADR を書き換えないこと。** その時点で何を考えたかが記録の価値であり、
上書きすると判断の履歴が消える。関係を明示して残す。

### 5-2. 足りない記述を書く

- 一般的でない選択をしたなら ADR を1つ足す（§2 の型）
- 処理の流れが増えたなら `docs-public/architecture.md` の該当フローに足す
- 新しい落とし穴を踏んだなら `*/CLAUDE.md` の該当節に足す

### 5-3. 経験を残す

詰まった過程・失敗した操作・テストが捕まえたバグは `docs/`（Git 管理外）へ。
**「何が起きたか」より「どう切り分けたか」を厚く書く。**

### 5-4. 確認

```bash
git status    # docs/ が staged になっていないこと
```

コミットは分ける。

```
feat(auth): Googleログインを追加
docs(auth): Googleログインの仕様と設計判断を記録
```
