# 開発者向けドキュメント

DishBoard の現在の実装、データの扱い、設計判断を公開情報だけで説明する。
初めて読む場合は、アーキテクチャ → データ設計 → API → 開発手順の順に読むと、コードとの対応を追いやすい。

## 現在の仕様

| 文書 | 読む目的 |
|---|---|
| [アーキテクチャ](architecture.md) | プロセス構成、責務の境界、主要な処理フロー、採用理由 |
| [データ設計](data-model.md) | モデルの関係、スナップショット、単位、更新と削除の意味 |
| [Web API](api.md) | HTTP の入口、認証、Web と MCP の契約の違い |
| [MCP](mcp.md) | ツール一覧、食品検索、確認付き操作、食数、再送防止 |
| [認証とアカウント連携](google-authentication.md) | DRF Token・Django セッション・OAuth の役割と Google 連携 |
| [開発手順](development.md) | ローカル起動、設定の読み込み、テスト、変更箇所の探し方 |
| [運用と更新](operations.md) | 本番構成、バックアップ、マイグレーション、食品再投入、反映確認 |

## 文書の更新先

現在の仕様は上表の文書を更新し、判断を変更した理由は ADR に追記する。
過去の ADR 本文は書き換えず、後続の判断へのリンクを冒頭に追加する。
実装上の細かな引数・制約は、各文書からリンクしたソースとテストで確認する。

リポジトリの作業規約は [CLAUDE.md](../CLAUDE.md)、各作業の手順は
[.claude/skills](../.claude/skills) にある。これらは実装の説明とは役割を分ける。
`docs/` は Git 管理外の個人メモであり、公開ドキュメントを理解するための前提にはしない。

公開資料には環境変数名・一般化した手順だけを書き、秘密値、実際のホスト名、アカウント情報、
利用者の食事・体重データを含めない。文書に機能が記載されていても、本番への反映済みを意味しない。
