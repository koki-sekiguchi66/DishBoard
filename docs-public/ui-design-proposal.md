# UIデザイン刷新提案：食堂の掲示板

> **採用済み。** この提案は採用され、実装済み。決定そのものは
> [decisions.md #21](decisions.md#21-uiの配色意匠を食堂の掲示板に刷新する) に記録している。
> このファイルは「なぜこの方向を考えたか」という調査・検討過程のメモとして残す。

## 0. これは何か

「AIチックなUIを避け、使い続けたくなるデザインにしたい」という要望を受けて調査・検討した内容の記録。
decisions.md の ADR が「決定」だけを短く記録するのに対し、こちらは調査した実例・比較した案・
却下した理由まで含む検討過程のメモという位置づけ。

インタラクティブなモックアップ（配色を昼/夜で切り替えられる）を別途 Artifact として作成し、
Claude との会話内で共有した。本ドキュメントの画像はその静止画版。

## 1. 現状の課題：何が「AIっぽい」のか

`frontend/src/index.css` の現在のトークンを見ると、原因は具体的に特定できる。

```css
--background: oklch(0.145 0.005 286);   /* 青紫寄りの無彩色グレー、ほぼ黒 */
--card: oklch(0.185 0.005 286);
--radius: 0.625rem;                     /* すべてのカードに一律の角丸 */
```

1. **背景・カードの無彩色グレー（色相286＝青紫寄り）** — shadcn/ui の既定ダークテーマそのもので、
   ChatGPT 系のツールや量産型の管理画面ダッシュボードに極めて広く使われている配色。
   「初期設定のまま」感が強く、"またAIに作らせたアプリ" という印象につながりやすい。
2. **コンテンツの種類を問わず、すべてが同じ角丸カード + ぼんやりした影** — 食事記録もPFCサマリーも
   設定項目も、同じ `Card` コンポーネントの器に入っている。器の形からは何も伝わらない。
3. **lucide-react の汎用線アイコンがそのまま使われている** — `UtensilsCrossed`・`Scale` など、
   意味は伝わるが「DishBoardらしさ」を持たない。他の無数のアプリと同じアイコンセット。
4. **`CharacterGreeting` のキャラクターが絵文字のプレースホルダーのまま** — ストリークやレベル表示の
   枠だけがあり、中身の人格がない。実装コメントにも「将来イラストに差替え」と明記されている
   （つまりこの課題は既に自覚されていた）。

裏を返すと、**土台（Tailwind v4 + shadcn/ui）自体に問題はない**。問題はその上に
DishBoard 固有の語彙を何も足していないことにある。

## 2. 目指す方向性：「ダッシュボードではなく、食堂の掲示板に」

アプリ名 "Dish**board**" の "board" を、抽象的な管理画面の意味ではなく
**文字通りの黒板・掲示板・食券**として扱う。

| 画面・要素 | メタファー |
|---|---|
| 記録ページの見出し部 | 今日の献立を書く**黒板** |
| 1件1件の食事記録 | 手渡しされる**食券**（ミシン目・スタンプ） |
| 分析ページ | 方眼ノートの**家計簿** |
| キャラクター | 掲示板の前に立つ**マスコット**（おにぎり） |

この発想は思いつきではなく、既存コードに前例がある。`MeasureField` の目盛り帯は
「キッチンスケールの指針」をなぞる意匠で、ADR にこう記録されている。

> 汎用のステッパーより「このアプリの部品」として馴染むことを狙っている
> （[decisions.md #18](decisions.md#18-数値入力を専用コンポーネントに寄せキーボード以外の手段を用意する)）

今回の提案は、**この考え方を1コンポーネントからアプリ全体へ広げる**ことに等しい。
「食」という具体的な題材から意匠を借りることが、量産型に見えないための一番確実な方法だと考えた。

## 3. 調査：参照した実例

思いつきで意匠を決めないよう、実在するアプリ・サイトを調べた。

**Cookpad**（実測値。マーケティングサイトの computed style を直接取得）

```
background-color: rgb(248, 246, 242)   /* 生成りに近い紙色。純白でも純グレーでもない */
accent color:      rgb(255, 153, 51)   /* 橙 */
```

「ユーザーの暮らしに寄り添う体験設計」を掲げており、コーポレートな配色ではなく
**紙のような生成り色**を基調にしている点が参考になった。

**YAMAP「RIDGE DESIGN」**

2020年のブランドリニューアルで策定されたデザイン原則。アイコン1つ1つに時間をかけて
「YAMAPらしさ」を作り込んでいることで知られる（[note記事](https://note.yamap.com/n/n1875c30510f0)）。
汎用アイコンセットをそのまま使わず、サービス固有の視覚言語を持つことの効果を裏付ける実例として参照した。

**2026年のUI/UXトレンド調査**（複数の記事を横断的に確認）

> AIが「完璧に整ったデザイン」を1秒で生成できるようになった今、人間に求められているのは、
> あえてその完璧さを崩す「遊び心」。手書きやアナログを混ぜる「混合型レトロ」が本格化し、
> 不完全さを敢えて残す表現が増える。

この指摘は今回の課題認識（1章）と直接一致する。ちょうど良い偶然ではなく、
「AI生成物と同じに見える」という問題自体が、今まさに業界で言語化されている最中だということ。

出典:
- [クックパッド公式サイト](https://cookpad.com)
- [YAMAPのデザイン原則「RIDGE DESIGN」が生まれるまで](https://note.yamap.com/n/n1875c30510f0)
- [2026年デザイントレンド予想](https://tld.holy.jp/2025/12/20/2026trend/)

## 4. デザイン言語

### 4-1. カラー

現在の `--primary`（`oklch(0.607 0.213 16.57)`）は色相16.57で、実はすでに赤というより
**朱色（vermilion）に近い**。これは変えず、「SaaSのアクセントカラー」ではなく
**食券のスタンプ・鳥居や印鑑の朱色**という意味づけに変える（使う面積は減らし、
スタンプ・強調に絞る）。変えるのは無彩色側——色相286（青紫寄り）の背景・カード・ボーダーを、
色相70前後（生成り〜黄土）に寄せた「紙」「黒板」の色に置き換える。

| トークン | 役割 | 現行（提案前） | 提案（昼） | 提案（夜） |
|---|---|---|---|---|
| `bg` | ページ背景 | `oklch(1 0 0)` 純白 / `oklch(0.145 0.005 286)` 無彩色黒 | `#e7dfc7` コルクボード | `#1c2420` 黒板の黒 |
| `surface` | カード・食券の紙 | `oklch(1 0 0)` | `#f3edd9` | `#26312a` |
| `board` | 見出し部・黒板 | （なし） | `#2b372e` | `#14201a` |
| `stamp` | ブランド強調・CTA | `oklch(0.607 0.213 16.57)`（据え置き） | `#c43b24` | `#e2593b` |
| `ink` / `chalk` | 本文・見出し文字 | `oklch(0.985 0 0)` / `oklch(0.13 0 0)` | `#2b2620` | `#ede6d2` |

PFC の色分けは既存の意味づけ（protein＝寒色 / fat＝黄 / carbs＝緑）を踏襲し、
彩度と色相だけを紙・黒板の基調に馴染むよう調整する（`sakana` 青 / `mustard` 黄土 / `matcha` 緑）。

### 4-2. タイポグラフィ

本文・見出しとも **Noto Sans JP を維持する**。新規Webフォントの追加は行わない方針。

理由は2つ。第一に可読性——記録・分析画面は数値を素早く読み書きする場面が中心で、
装飾的な書体は不向き。第二に依存関係——このアプリは
「ライブラリ・依存の追加は事前確認」（`CLAUDE.md`）という制約と、
1GB VMという実行環境の制約を持つ。書体を足す前に、**太さ・余白・わずかな傾き**という
CSSだけで表現できる範囲でどこまで「声」を出せるかを先に試す。

数値（kcal・g）は等幅フォント（`ui-monospace`）+ `tabular-nums` で揃え、
食券に刻印されたような見た目にする。

### 4-3. 形とテクスチャ（コンテンツ種別ごとのメタファー）

現状は「食事記録」も「PFCサマリー」も同じ角丸カードに入っているため、器の形から
情報の種類が伝わらない。コンテンツの性質ごとに器の形を変える。

| コンテンツ | メタファー | 形状の特徴 |
|---|---|---|
| 記録ページ見出し + タブ | 黒板 | 濃い緑黒、チョークの粉のようなノイズ、下線は手書き風の曲線 |
| 1件の食事記録 | 食券 | 左端にミシン目（穴の列）、わずかな傾き、円形スタンプでkcal表示 |
| 分析ページ | 家計簿 | 方眼の罫線を背景に敷いた棒グラフ・一覧 |
| PFCゲージ | キッチンスケールの目盛り | `MeasureField`（ADR #18）と同じ目盛り帯の意匠を流用し、統一感を持たせる |

### 4-4. キャラクター

`CharacterGreeting` の絵文字プレースホルダーを、シンプルな線画のマスコット（おにぎり）に置き換える案。
複雑な質感（3Dレンダリング・グラデーション多用）は避け、**太さの揃った線 + フラットな色面**
2〜3色で構成する。最低限、以下の状態を用意すれば主要な場面をカバーできる。

- 通常（挨拶・待機）
- 達成・お祝い（目標達成、ストリーク更新）
- 応援・声かけ（記録が途切れている、エラー時）

すでに実装されている「🔥 ストリーク」「⭐ Lv.」の表示枠は、キャラクターと組み合わせて
初めて意味を持つ。枠だけの状態を長く放置しない。

### 4-5. モーション

記録の保存など「確定」の操作に、食券にスタンプを押すような短いスケールバウンスを検討する。
`MeasureField` のドラッグ操作にはすでに固有のイージングがあるため、新しいモーションを増やすのではなく
**既存の動きの語彙に合わせる**。`prefers-reduced-motion` の尊重は既存踏襲。

### 4-6. アイコン

すべてのアイコンを置き換える必要はない。閉じる・シェブロン・チェックのような
「操作」を表すアイコンは lucide-react のまま流用してよい。一方、
「食事」「体重」「目標」のように**DishBoard固有の意味を持つ**アイコンだけを、
マスコットと同じ線の太さで揃えた自作SVGに差し替える。数は10〜15程度で足りる想定。

## 6. 変えないもの

CLAUDE.md の「既存アーキテクチャを許可なく変更しない」という制約に沿い、
この提案は **見た目の層に閉じる**ことを前提にしている。

- Tailwind v4 + shadcn/ui のprimitive自体は残す。CSS変数（トークン）と、
  食事記録・分析ページなど一部コンポーネントの表現だけを変更する
- `MeasureField` の入力ロジック・テスト（キーボード / ステッパー / ドラッグ）は無変更。
  意匠面のみ、目盛り帯の見た目をアプリ全体のPFCゲージ等に拡張する
- React Router 不使用、feature構成、状態管理の方針など、フロントの構造には手を入れない
- バックエンド・データモデルは対象外

## 7. 実装した場合の影響範囲・要確認事項

- `index.css` のトークン全面置換は、CSS変数経由で参照している既存コンポーネントに
  自動的に波及する（コンポーネント側の変更は基本的に不要）
- マスコット・独自アイコンのSVGアセットを新規に追加する。
  「独自のボタン・カードを作らず `@/components/ui/*` を使う」という規約は
  操作コンポーネントに対するものであり、装飾用SVGはその対象外という理解だが、
  実装前に認識をすり合わせたい
- 新規Webフォントは追加しない方針（4-2）。将来的に手書き風フォントを試す場合は、
  `CLAUDE.md` の「ライブラリの追加は事前確認」に基づき別途相談する
- フロントの Vitest はロジック中心のテストで、見た目のスナップショットテストは持っていない。
  大規模な意匠変更でもテストスイート自体は通る見込みだが、裏を返すと
  **見た目の崩れをテストでは検知できない**ため、変更後は主要画面を手動で確認する
- ライト・ダーク双方で、既存のコントラスト基準（AAA 7:1、[decisions.md #14](decisions.md#14-ダークテーマを既定とし初期化をインラインスクリプトで行う)）を再検証する
